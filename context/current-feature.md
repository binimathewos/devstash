# Current Feature: Rate Limiting for Auth

Add rate limiting to auth endpoints to prevent brute force, credential stuffing, and email-endpoint abuse.

## Status

In Progress

## Goals

- Create a reusable `src/lib/rate-limit.ts` utility backed by Upstash Redis (`@upstash/ratelimit`, sliding window)
- Protect these endpoints with the listed limits/windows/keys:
  - `/api/auth/callback/credentials` (login) — 5 attempts / 15 min, keyed by IP + email
  - `/api/auth/register` — 3 attempts / 1 hour, keyed by IP
  - `/api/auth/forgot-password` — 3 attempts / 1 hour, keyed by IP
  - `/api/auth/reset-password` — 5 attempts / 15 min, keyed by IP
  - `/api/auth/resend-verification` — 3 attempts / 15 min, keyed by IP + email
- Return 429 with `{ error: "Too many attempts. Please try again in X minutes." }` and a `Retry-After` header when limited
- Surface user-friendly errors on the frontend via toast notifications

## Notes

- Per `context/features/rate-limiting-spec.md`
- Rate limit utility extracts IP from `x-forwarded-for` (Vercel) and combines IP + identifier (email) where applicable
- Checks return `{ success, remaining, reset }`
- Fail open (allow the request) if Upstash is unavailable
- Login limiting is tricky with NextAuth credentials — `/api/auth/callback/credentials` is handled internally by NextAuth, so this likely needs a custom approach (e.g. checking limits inside the `authorize` callback) rather than wrapping the route directly
- New env vars: `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN`
- Upstash free tier (10k req/day) should be sufficient

Reset tokens are namespaced with a `reset:<email>` `identifier` prefix (module-level `RESET_IDENTIFIER_PREFIX` + `resetIdentifier()`) so they never collide with email-verification tokens (which store the plain lowercased email) — `checkPasswordResetToken` rejects any token whose identifier lacks the prefix, keeping the verify/reset flows independent. `src/lib/email.ts` gained `sendPasswordResetEmail` (mirrors `sendVerificationEmail` styling/`getBaseUrl`, reset link → `/reset-password?token=`, "expires in 1 hour" copy). **API** (both `{ success, data?, error? }`): `POST /api/auth/forgot-password` looks up the lowercased email and only sends when `user?.password` exists (GitHub/OAuth-only accounts silently no-op), wraps the send in try/catch (best-effort), and **always returns 200** — no account enumeration (mirrors `resend-verification`); `POST /api/auth/reset-password` validates token + min-8 + match (manual validation, not Zod — consistent with register), bcrypt-hashes @ 12 rounds, calls `resetPasswordWithToken`, and maps `expired`/`invalid` to distinct 400 messages. **UI** (server-page → client-form, shared `AuthCard`): `/forgot-password` ([page](src/app/forgot-password/page.tsx) + `ForgotPasswordForm`) — email request → neutral "if an account exists…" confirmation panel; `/reset-password` ([page](src/app/reset-password/page.tsx) is an async server component that validates the token via `checkPasswordResetToken` on load and renders an invalid/expired message + "request a new link" instead of a dead-end form) + `ResetPasswordForm` (new password + confirm, min-8 client validation, success → `/sign-in?reset=1`). `SignInForm` got a "Forgot password?" link in the password label row and a `?reset=1` success notice ("Password reset — sign in with your new password."); `sign-in/page.tsx` threads the new `reset` searchParam through. Both new pages are public (proxy only gates `/dashboard` + `/profile`). `npm run lint` and `npm run build` pass (build registers all 4 new routes; `/forgot-password` static, `/reset-password` dynamic). Live browser/email round-trip not yet exercised — same Resend limitation as the verification features (no sending domain linked, so reset emails currently only reach the Resend account owner); for local testing, pull the token from the `VerificationToken` row and hit `/reset-password?token=...` directly.
